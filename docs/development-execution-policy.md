# 后续开发执行指南

版本：`phase-execution-v2`。适用于用户后续授权、尚未冻结计划的 Phase014–Phase137。先读本指南和 [测试执行政策](testing-execution-policy.md)，再读取当前卡及其必需输入。

本指南优先解释旧文档中的通用复核、等待和收尾流程；业务断言、分母、阈值、里程碑专用全量、指定的独立 reviewer 数量及双 shell seal 继续完整满足。测试范围和跨 attempt 产品结果复用仍由原测试政策决定：自动 affected 选测尚未实现，跨 attempt 缓存仍为 `disabled`，Phase014、Phase015 仍使用 `full`。

修订依据：Phase013 的五次仓库全量合计约27分31秒，正式自动验收合计约59分钟（已包含全量）；多轮独立复核累计接近5小时，部分与开发并行。最后在235项来源中确认230项未变，以差异终审约13分17秒完成。[实际复核范围](evidence/attempts/Phase013/attempt-7/independent-review-assessment-closeout-attempt-7.json)说明了引用旧审查与核对当前证据的区别。本次立即优化复核和收尾安排，不承诺未经测量的提速比例。

## 1. 每卡采用一条收尾流程

1. 核对已同步 HEAD、上一 checkpoint、固定输入和授权范围，冻结本卡断言、修改范围与正式验收集合。
2. 修改期间先跑失败项、新增断言和受影响检查；汇总已知问题，局部修复稳定后再启动昂贵的完整正式验收。
3. 指定未参与实现的独立 reviewer。必要时让同一 reviewer 提前检查高风险业务、断言和报告结构，再核对最终证据；提前介入不新增默认必经轮次。当前卡另有多位业务 reviewer 的要求照常执行。
4. 先通过下节预检，再运行冻结的完整验收。正式验收后保持候选稳定，按第3节完成独立复核，再执行双提交、双 shell seal 和远端核对。
5. 复核发现问题时记录可复现触发、违反的本卡要求和最小修复范围；汇总同轮已知问题后一起处理。影响当前业务或验收可信度的缺陷必须关闭；纯风格建议和无当前缺陷依据的通用设施扩建，不追加为封口条件。

## 2. 将可预见的收尾失败前置

- 昂贵验收前确认命令存在、输入齐全、测试能收集、fixture 可用、报告可解析；完成适用的类型、格式、计划、路径及摘要检查。
- 新增或修改 runner、collector、证据校验器时，先用隔离 fixture 检查缺失、篡改、遗漏断言和错误来源是否被拒绝。复用已有检查入口，避免每卡重写同类校验或无限增加检查器层级。
- 生成报告前检查最长拟提交路径在当前 Windows/Git 下可读；按需要使用单次命令或仓库级 `core.longpaths`。归档优先引用已有不可变路径/hash，确需副本时用当前 attempt 下的短路径，避免嵌套复制历史目录。
- 受测文本按 `.gitattributes` 规范化 LF，前置执行适用的格式检查和 `git diff --check`；正式暂存后仍执行 `git diff --cached --check` 并核对 blob 字节。历史原始证据的空白问题按精确路径及既有规则处理，不改写其字节。
- 秘密、占位和未实现代码扫描先核实上下文，区分真实秘密/缺失实现与测试占位、文档引用、故障反例。真实秘密不得进入产物；误报精确处置，不全局关闭扫描，也不为消除词命中修改冻结报告。

## 3. 完整审查后默认采用差异复核

每卡首轮语义审查覆盖本卡改动、受影响调用链、业务契约及相应断言。`sourcePaths` 是完整性核验集合，不要求逐行重读所有未变历史文件。修复后的差异复核沿用已完成的审查工作，不沿用旧 attempt 的产品通过结论。

前提是存在可核验的完整独立审查记录，包含来源快照、实际检查范围与未关闭意见。前次结论可以是 FAIL，但只读过部分内容的中断输出不能冒充完整审查。

1. 独立核验前次审查及其 basis，再对当前全部声明来源、计划与报告重算摘要。
2. 比较来源集合，明确新增、修改、删除及重命名前后路径；reviewer 检查变化及受影响的数据流/消费者、所有未关闭意见和修复对应的当前断言。
3. 当前完整验收集合、分母、反向验证、原始报告来源和适用截图仍逐项核对。未变语义范围可以引用已绑定的前次完整审查，在最终记录中说明引用范围。
4. 新增边界、依赖变化、前次缺项或影响不明时扩大相应范围；无法核验前次来源时补齐完整审查，不猜测无影响。
5. 最终报告绑定当前 `planHash`、来源和报告摘要、独立 reviewer 身份，处置所有阻断意见，明确本次实际检查与沿用的范围；不得把前次 FAIL 或中断结果直接标为 PASS。

reviewer 默认读取现有实现和证据。当前卡明确要求 reviewer 执行的检查照常执行；发现疑点时先做最小复现，由主 agent 协调会改变环境的操作，不因换 reviewer 重启全量、build 或服务。

## 4. 复核有截止时间，缺项可交接

优先使用当前任务的原生独立子 agent，复用现有计划和 review 记录。派发说明写清本次范围、前次审查/basis、变化和未关闭意见、开始时间、截止时间及交付位置；不为普通复核新增 Gate、schema 或重复清单。

| 项目 | 默认安排 |
|---|---|
| 每位 reviewer 的完整复核 | 45分钟 |
| 已有完整审查后的差异复核 | 20分钟 |
| 进展检查 | 约每5分钟核对已验证范围、问题和剩余项 |
| 无可核验进展 | 连续10分钟时保存交接并停止原进程 |
| 服务失败/限流 | 连续3次失败，或累计等待5分钟，停止原通道并接续 |

主 agent 按墙钟管理预算，每次阻塞等待不超过60秒；原生子 agent 到界限时主动中断并收集已完成项。确需外部 CLI 时，启动前配置进程超时和任务专属终止方式，不能只无限等待进程退出。重启、重连计数归零和换 reviewer 都不清零同一逻辑复核的累计耗时。

到界限或工具中断时保存 `INCOMPLETE` 交接：当前 basis、已检查范围、未检查范围、已发现问题、未关闭意见及下一步。它是调度状态，不是 Gate PASS，不改变既有 Gate 枚举。接续 reviewer 先验证交接及当前来源，只完成缺项和变化；中断输出不能替代尚未完成的独立结论。

同一稳定候选最多自动更换进程接续一次，并使用原预算剩余时间。预算耗尽或仍无结果时，必须明确报告未完成范围，处理环境原因或重新拆分剩余对象；不得重新派发相同完整审查继续等待。大型里程碑可在首次派发前按实际对象划分范围和预算，保留规定的独立性与人数，不能事后以“大任务”为由无限延长。

## 5. 完整核验，精简读取

- 摘要、JSON/schema、计数、集合及历史完整性比较交给已有脚本，保留完整机器记录；传给 reviewer 的输出默认只含数量、差异路径、不匹配项和未关闭问题。
- reviewer 从索引定位当前原始报告与相关源码，摘要相等仅证明字节一致，不代替代码语义和断言审查。工具输出截断时缩小范围，不重复原样打印巨量报告。
- 状态轮询使用紧凑结果；没有变化时不重新读取全部事件或历史。向用户报告新发现、已关闭问题及下一步，避免连续重复“仍在等待”。

## 6. 返工按实际变化处理

| 情况 | 执行动作 |
|---|---|
| 调试中的业务、测试或设施失败 | 先跑失败项和相关检查；已知问题修复稳定后，执行冻结的正式集合 |
| 正式验收后产品、测试、fixture、计划或执行脚本改变 | 保留旧 attempt，按测试政策在新 attempt 执行全部当前要求；独立复核采用上述差异方式 |
| 仅 reviewer 中断，受测来源、计划、原始报告均未变 | 接续缺失审查，沿用当前 attempt 的真实证据，检查交接期间无字节变化 |
| artifact 未变，仅 metadata、seal 或推送中断 | 按既有协议核对原 artifact、报告及提交关系，只恢复对应步骤 |
| 仅文档维护 | 执行相称的文档、脚本及准入检查，不启动产品 Phase 或推进 run state |

修改证据校验代码不等于 metadata-only。跨 attempt 复用仍未实现，不能仅以“产品没改”为由跳过新 attempt 正式验收。该能力如另行实施，应先满足测试政策第7节的来源与失效校验；本指南不授权为节约一次测试临时开发缓存系统。

计时使用现有执行记录：分别保留实现/设施、正式验收、独立复核、服务等待及封口的起止、次数与重复原因；有并行时分别报告，不将重叠时段相加。无法测量的项写 `null/UNMEASURED`，不把总任务时长全算作测试或限流。
