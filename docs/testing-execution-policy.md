# 后续阶段测试执行政策

版本：`phase-verification-v1`。适用范围：用户后续授权的 Phase013–Phase137；本次文档维护不执行 Phase013。

本政策根据用户“优化后续开发文档”的授权制定，补充现有 manifest 与八份冻结公共输入。原 manifest、冻结输入、任务卡和 Phase000–Phase012 的计划、Gate、提交引用及 hash 保持原字节，不刷新旧摘要。

未来计划尚未冻结时，本政策优先于旧公共契约及任务卡中重复的通用全量测试模板，决定执行顺序、工程回归范围和重复报告的处理。任务卡的业务断言、明确要求的专用全量、固定场景、分母、阈值、故障注入和审计要求不变；已经冻结的计划不得借此删减 requiredCaseIds 或缩小原定命令范围。

立即采用第 2、5、6 节中现有 runner 能表达的安排。`affected` 选择和同次执行的报告映射必须先具备可验证实现；跨 attempt 结果复用保持 `disabled`。本文件不代表这些能力已经实现，也不创建新的产品命令。

## 1. 三种范围分别记录

| 范围 | 含义 | 完成依据 |
|---|---|---|
| 本卡完整验收 | 当前卡全部 requiredCaseIds、业务断言、反向测试和追加回归 | results 与冻结计划精确相等，每项真实通过 |
| 仓库全量回归 | 当前项目测试配置发现的全部产品测试 | 记录实际发现和执行集合、数量及原始报告；零匹配或静默跳过不是通过 |
| 专用完整验收 | 卡片明确规定的里程碑、黄金集、回放、视觉、性能或可靠性集合 | 按原卡固定范围、环境、样本和阈值完整执行 |

未来计划使用 `testMode=full|affected` 表示工程回归选择方式，不改变本卡完整验收。`full` 包含仓库全量回归；`affected` 包含本卡全部必测项和可证明受影响的既有回归。浏览器、数据库、构建及专用验收不是运行一次 Vitest 就自动完成。

本卡明确要求的 lint、typecheck、format、build、数据库和浏览器检查继续保留。`testMode` 不隐含删除这些命令；仅文档维护按实际改动执行适当检查，不冒充产品 Phase。

## 2. 执行顺序：先消除低成本失败，再收尾验收

1. 开始时核对 Git 状态、上一 checkpoint、已同步 HEAD、冻结输入和当前授权范围；Phase013 前按第 8 节另外核对维护提交。读取本卡及直接依赖，不为确认旧 Gate 再执行所有上游 Phase runner。
2. 实现前冻结 requiredCaseIds、业务分母、输入/输出、修改范围和验证命令。记录第 3 节选出的 testMode、理由和影响范围；不填入尚未生产的 npm script。
3. 修改期间先跑失败项、新增断言和已确认的受影响测试。诊断输出保存为诊断结果；局部通过不授予 Gate PASS。
4. 在昂贵测试前完成适用的 LF/格式、lint/typecheck、计划与 schema、路径/hash、测试收集和 fixture 检查。先确认命令存在、报告能解析、分母有对应断言以及环境就绪。
5. 涉及验收脚本时先做其隔离自检：缺输入、篡改报告、遗漏 case、错误提交关系必须失败；需要双 shell 兼容的脚本先验证两种 shell 的行为，再投入产品完整验收。
6. 对容易在收尾返工的业务或验收脚本，可让最终独立 reviewer 在实现期间提前检查业务遗漏、断言、权限、计划和报告结构，再于正式证据齐全后完成最终复核。这是同一复核工作的前置安排，不新增每卡必经的独立评审轮次，也不替代指定的两次业务 reviewer。
7. 确认受测文本已规范化、fixture 和计划稳定后，运行一次最终所需完整集合：本卡完整验收、选定工程回归、专用命令及真实反向测试。可在冻结计划时合并有证明的重复执行，规则见第 5 节。
8. 最终独立 reviewer 核查实际受测代码、断言、原始报告和适用截图，绑定当前 planHash 与 reviewerRunId，关闭全部阻断意见。最终复核仍完整保留。
9. 按原协议形成 artifact、直接子 metadata、双 shell seal 和远端同步。复核或封口发现问题时先分类，再决定恢复范围，不能把“只跑一次”当作不复验失败的理由。

实现、测试设施、实际测试、独立复核和证据整理分别记账。记录执行次数、耗时、数据库准备时间及重复执行原因；未测量写 null/UNMEASURED，不承诺固定提速比例。

## 3. 未来计划的 testMode 判定

按下表从上向下判断，命中 `full` 后不能以“改动行数少”降为 `affected`。选择发生在计划冻结前，执行期间新发现更大影响范围时扩充计划并保留旧 attempt/hash。

旧通用提交模板里单独列出的 `npm run test` 按本节选择实际参数，不自动视为业务专用全量。任务卡明确指定的集合、场景、数量、里程碑范围及强制重跑语义必须完整保留；无法区分通用模板与业务完整验收时采用 `full`。

| 变化或阶段 | testMode | 要求 |
|---|---|---|
| 当前卡是 manifest 中的里程碑收口卡 | full | 仓库全量及该里程碑专用完整验收均执行 |
| 当前卡明确要求全量回归、发布验证或修复后的专用完整执行集 | full | 保留卡片定义的专用范围，不能改成抽样；普通的“本卡全部通过”不单独触发此行 |
| 鉴权、会话、密钥、权限、隐私或公共安全边界变化 | full | 同时覆盖未授权、撤销、泄漏及失败原子性等原定负例 |
| Prisma schema、迁移、seed、数据库权限或共享持久化协议变化 | full | 使用真实隔离 PostgreSQL，保留迁移和并发验收 |
| 公共 DTO、状态机、环境解析、共享组件/布局或跨模块基础服务变化 | full | 覆盖已实现消费者；未知消费者不得视为无影响 |
| 依赖锁、运行时、构建/测试配置、fixture loader 或 runner/报告判定逻辑变化 | full | 先验证基础设施，再验证产品集合 |
| 映射缺失、动态依赖不明、删除/重命名覆盖不全或无法证明选择正确 | full | 默认回退，不以人工声明代替映射 |
| 普通阶段仅修改独立模块或独立 UI，且全部通过第 4 节准入 | affected | 本卡全项加闭包回归；相关浏览器与构建要求照常执行 |

Phase013 涉及密钥与管理员安全，选择 `full`；Phase014 是 M3 收口，选择 `full`；Phase015 改数据库与 Provider 治理基础，选择 `full`。后续只修改独立 UI 展示且不触及共享组件、布局、DTO 或安全边界时，才可能选择 `affected`。

后续里程碑结束编号从冻结 manifest 读取；当前为 014、018、021、050、060、073、081、088、100、137。其他专用收口和发布卡仍依原任务要求，不用这份编号列表覆盖它们。

## 4. affected 的启用条件

仅在当前 runner 能生成并验证以下证据时启用；任一项不支持即执行 `full`，不要先缩减命令再补证明。

- 冻结对比基线和当前改动集合，覆盖工作树及本卡恢复提交的全部变化；删除保留旧路径，重命名同时检查旧、新路径。
- 对每个改动列出生产者、消费者、直接及传递依赖、相应测试文件和断言映射；数据库/路由注册、动态加载、配置与生成器等依赖不能只靠静态 import 推断。
- 记录测试发现全集、选择集合、选择理由及遗漏检查，确保本卡 requiredCaseIds 和专用完整集合全部包含；不是只记录几个文件名或 shell 过滤词。
- 选择器的隔离反向自检证明：删除消费者映射、漏选受影响测试、重命名遗失旧路径、配置变化错误命中旧选择，均被拒绝或回退 `full`。
- 选择集合有真实执行结果且没有静默 skip/零匹配；发生新失败或观察到未登记消费者时扩展闭包，不用调整预期掩盖遗漏。
- 独立 reviewer 能根据差异与映射核对范围。公共风险触发器仍按第 3 节直接使用 `full`，不能因为有映射而绕开。

不创建“受影响”状态替代 case PASS，不修改 schema 中的结果含义。实现该选择能力时，先保存自检与回退证据，再在新冻结计划里声明 `testMode=affected`。

## 5. 同次验收去重与报告映射

优先在计划冻结时安排一份实际执行覆盖多个验收项，例如一次全量报告已经包含本卡目标测试。它是同一次执行的证据共享，不是从旧 attempt 取回绿灯。

- 保留实际命令及参数、退出码、测试发现/执行集合、逐项断言、fixture/环境与输入输出 hash；没有运行的定向命令不得记录为已执行。
- 每个 requiredCaseId 必须有机器可核对的映射，指向原始报告中的具体断言及对应分母。报告总体 PASS、文件存在或测试名字相似都不足以证明覆盖。
- 多个 case 可以引用同一原始报告，但 results 中每个 testCaseId 恰好一次；报告执行次数与唯一业务场景数分别统计，不增加分母。
- 本卡要求的额外数据库、浏览器、反向验证或故障注入，只有报告包含它们的真实执行证据时才算覆盖。正常路径测试不能充当反向测试。
- 已冻结计划要求独立命令，或当前 collector 无法验证映射时，继续执行原命令；不手工复制 PASS，不伪造输出，也不删除旧计划要求。

上游回归优先调用当前已有的测试入口，避免再启动上游 Phase 的 prepare/verify/complete 整套事务。旧 Gate、计划、hash 与提交链仍由当前校验器完整核验；本卡明确要求的历史隔离重放照常执行。

安全的基础设施优化可复用确定性 fixture loader、只读模板和受控进程准备，但各测试仍使用隔离数据。连接复用不等于共享污染库，旧数据库快照或机器缓存不自动成为通过证据。

## 6. 收尾失败按范围恢复

| 情况 | 恢复动作 |
|---|---|
| 产品测试或反向测试失败 | 保存失败 attempt，修复后先局部诊断，再按当前计划重新完整验收 |
| 仅 metadata 生成中断，artifact 及其报告、计划和复核字节未变 | 校验原 artifact、输入输出 hash 与报告，依既有恢复协议重建未封口 metadata；无需重跑产品测试 |
| metadata 已提交但尚未 seal | 先只读重跑双 shell validator；通过后继续同步，不默认重新执行产品 runner |
| 双 shell seal 已通过，仅推送失败 | 保留本地提交，重验 seal 并重试常规推送，核对远端；不新建 Gate |
| 产品、测试、fixture、验收脚本或其他 artifact 内容改变 | 形成当前卡的新 attempt 并重新验收；第 7 节未启用前不沿用旧 attempt 的产品结果 |

metadata-only 恢复以 artifact 不变为前提；不能把修改 seal 脚本称为“仅元数据”，也不能只改 Gate 的 commit/tree 字段来迁移结果。已经封口的 Gate、metadata 和历史 hash 永不覆盖。

“一次最终完整集合”是减少无依据重复的执行安排，不保证任何失败后仍只执行一次。反向测试后的恢复、固定专用重跑及 reviewer 发现问题后的验证要求继续满足。

## 7. 跨 attempt 结果复用：disabled

当前政策不启用跨 attempt 缓存，不跨 Phase 复用测试结论。只有后续授权工作实现并通过以下验证，才能为同一 Phase 的后续新计划显式启用；本次文档维护不完成该实现。

1. 原始报告不可变，具有 source attempt、实际命令、报告路径/hash、受测文件来源和完整来源链；不能把旧报告重新标成当前执行。
2. 依赖摘要涵盖源码及传递依赖、测试/fixture、迁移/seed、生成器、锁文件、运行时、环境配置、命令/参数、选择集合及策略版本。无法列全依赖时该项必须重跑。
3. runner 自动核对摘要、发现集合、环境和当前 requiredCaseId 的断言语义，记录允许复用或失效的原因。mtime、文件名、整份报告 PASS 和“产品代码没改”均不能代替判断。
4. 隔离负例证明源码、fixture、迁移、锁文件、环境、命令、选择器、报告或策略变化后，陈旧结果被拒绝；来源缺失、伪造 hash、遗漏依赖和错误分母同样失败。
5. 当前最终 Gate 清楚区分实际执行与经验证引用，每个 requiredCaseId 仍完整满足；独立最终复核、反向验证和双 shell seal 不靠缓存跳过。

在这些能力未完成之前，按第 6 节恢复；不要为了节省一次全量而临时修改摘要规则或静默打开缓存。

## 8. Phase013 起的输入与历史衔接

本政策是项目根版本管理的补充输入，不加入原 `pinnedInputs`，不写入 manifest.runStatePinnedInputs，不替换 run state 的 manifestHash 或八份 contractHashes。

后续 `docs/phase-plans/PhaseNNN-inputs.json` 必须在保留原输入字段的同时记录以下两个独立对象；sha256 均读取实际 LF 字节，不能填示例值：

```text
checkpointMaintenance: {
  path: "docs/checkpoint-migrations/testing-policy-20260912.json",
  sha256: <维护收据实际 SHA-256>,
  commit: <包含该收据且已同步的维护提交完整 ID>
}
validationPolicy: {
  path: "docs/testing-execution-policy.md",
  sha256: <本文件实际 SHA-256>,
  version: "phase-verification-v1"
}
```

本文件同时纳入当前计划 `sourcePaths` 和最终 `Gate.inputs`，使用真实路径和 hash；input 收据自身及其维护链按正式校验器验证。不把补充输入伪装成历史冻结输入，不改写旧计划来补字段。

Phase012 的最后 metadata 仍是 `3fa20a8dca445859d94db8dfa1232d16f8a6e07f`。文档维护提交是独立维护历史；维护后已同步 HEAD 独立记录为未来阶段的实际开工位置，不替换该 metadata、既有 baselineCommit 或 checkpoint。维护收据不得把文档维护宣称为 Phase013 PASS。

首次消费本政策前，正式校验器须能核对维护收据与输入引用，并在缺失、篡改、错误提交或历史输入变化时失败。只支持本政策输入链不等于支持 `affected` 或缓存；这两项仍分别遵守第 4、7 节的能力门槛。

正式 Phase 继续要求全部当前验收通过、独立最终复核、artifact/metadata 直接父子双提交、双 shell seal、干净工作树、常规推送与远端核对。完成文档维护或一张卡不自动授权下一卡。
